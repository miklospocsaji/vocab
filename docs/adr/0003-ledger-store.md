# 0003 Ledger store

Status: accepted (2026-10-27; owner decision of 2026-10-26); amended 2026-11-06 (no private subnets, results in the ledger until M3) and 2026-11-13 (results in the ledger, build outputs in S3)

## Context

The ledger records work items, tasks, attempts, artifacts (as S3 pointers), SDK messages, token usage, cost and events. It feeds the console (M6) and the benchmark (M7), which need relational queries: cost per role per work item, success rate per role version, attempts per task.

## Decision

- Postgres on a dedicated Aurora Serverless v2 cluster for the factory, separate from the app's cluster. `serverlessV2MinCapacity: 0` with auto-pause, so an idle factory costs only storage.
- JSON artifacts and screenshots go to S3, keyed by work item and attempt. The ledger stores their keys.
- Locally (M1) the same schema runs in Postgres in Docker.
- Schema migrations are plain SQL files, applied by the deterministic runner.

## Alternatives

- DynamoDB: cheaper when idle and no VPC needed, but the console and benchmark queries would need precomputed aggregates.
- Sharing the app's Aurora cluster: cheaper, but couples factory experiments to app data and blast radius.

## Consequences

- The ledger needs a VPC. Lambdas and Fargate tasks that write to it run in private subnets (see the egress decision in the brief, section 8). Superseded by the amendment of 2026-11-06: public subnets only, and only the worker connects.
- Resuming from auto-pause takes roughly 15 seconds. Handlers use connection retries with a timeout long enough for it.
- Agents never connect to the ledger. The runner records on their behalf.

## Amendment 2026-11-06: no private subnets, results in the ledger until M3

With no egress control (ADR 0008, owner decision of 2026-11-02), the factory's VPC has public subnets only, in two AZs, with no NAT and no VPC endpoints:
- Aurora sits in those subnets with no public address (`publiclyAccessible: false`). Its security group has one ingress rule: port 5432 from the worker's security group. Connections use TLS, verified against the RDS CA bundle committed at `factory/ledger/certs/rds-global-bundle.pem`.
- Only the worker connects to the ledger. The webhook Lambda runs outside the VPC and never touches it, so no Lambda needs private subnets. This replaces the first consequence above.
- The ledger's credentials are generated by RDS into Secrets Manager and injected into the worker by ECS. `connectionFromSecret` builds the connection from that secret.
- Nothing wakes Aurora but the worker, so auto-pause holds while the factory is idle.

Until M3, a role's validated JSON result is stored on its attempt in the ledger (`attempts.result`), not in S3. One small result per attempt does not justify a bucket yet. S3 arrives in M3 with larger artifacts, as the brief's section 3 describes, and the ledger then stores their keys as decided above.

## Amendment 2026-11-13: results in the ledger, build outputs in S3

The amendment of 2026-11-06 planned S3 for every result from M3. M3 (add-build-loop) splits them instead:
- **Role results stay on their attempts in the ledger** (`attempts.result`), for every role: proposal, design, review, plan, classification, and the build roles' results from their outcomes. They are small JSON that the summary comments, the console (M6) and the benchmark (M7) query.
- **Build outputs go to S3.** These are large: patches, gate output, message streams. And the build task cannot reach the ledger (ADR 0011). Per task, under `work-items/<changeId>/tasks/<taskId>/`:
  - `next.json`, which build runs next
  - one folder per build attempt, `<role>/<n>/`, holding `input.json` from the worker, and `patch.diff`, `gates.json`, `messages.jsonl` and, last, `outcome.json` from the build

  The ledger keeps the attempt's prefix (`attempts.store_prefix`), its gates result and its classification. The worker replays `messages.jsonl` into the ledger, so tokens and cost are queried as before.
- **The bucket:** one per stack. It blocks all public access, refuses requests without TLS, uses S3-managed encryption, has no versioning, expires objects after 180 days, and is retained when the stack is deleted.
- **Access:**
  - The worker gets and puts `work-items/*` and may list that prefix, so that a missing key is a 404 rather than a 403.
  - The build task may only get and put `work-items/*`.
  - Locally, the same keys live under `~/.factory/store` (`FsStore`).
  - Both containers pick the store from `FACTORY_STORE_DIR` or `FACTORY_STORE_BUCKET`.
- Screenshots (M4) will follow the same pattern: objects in the bucket, keys in the ledger.
